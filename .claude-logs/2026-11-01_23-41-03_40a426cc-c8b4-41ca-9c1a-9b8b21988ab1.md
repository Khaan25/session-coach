Most likely no, not when you switch. You don't need `/clear`, but uploading at `SessionEnd` alone is the wrong trigger for app users.

**Why:**
- `SessionEnd` fires only when Claude Code ends a session. That happens on exit, `/clear`, logout, or when the process stops.
- In the Claude app, switching to a new chat doesn't end the old one. It stays in the sidebar, alive or idle, and you can go back and keep typing. So the hook probably doesn't fire when you switch.
- It probably fires later: when you archive the chat, quit the app, or the app closes the session. App quit is risky, because the app may kill the hook before the worker detaches.
- So under the current design, a chat you leave without ever ending uploads late or never. A chat you return to after it uploaded runs into the resume gap, and its new turns are dropped.

**The fix:** upload progressively from the `Stop` hook, which fires after every turn, as well as from `SessionEnd`. This repo's own `.claude/log-session.py` already does this: it rewrites the log after every turn so it never depends on the session ending.

For that to work, the server has to accept a re-upload of the same `session_id`. Today, a session that has already been processed gets `409` and its new turns are lost. Possible ways around that:
- Replace the log, then re-extract only the new turns.
- Upload in segments keyed by byte offset or a content hash.

Either one changes the `sessions` contract (the shared migration), so the team has to agree first. Uploading after every turn also means extraction can't run on each upload, or the cost multiplies. One option is to upload every turn but extract only after the session has been idle for N minutes.

I haven't tested what the app actually does on switch, archive or quit. The log hook doesn't record why `SessionEnd` fired, so the logs can't tell us.

Progressive upload means the `Stop` hook uploads after every turn, `SessionEnd` does a final flush, and extraction runs only once a session has been idle for N minutes.

## Pros

- **Works however the user leaves.** Switching chats, never running `/clear`, quitting the app, or a crash: the worst case is losing the last turn.
- **Closes the resume gap.** A resumed session keeps updating its own row, so new turns are no longer dropped.
- **Still no duplicate rows.** It stays one row per `session_id`, so the uniqueness rule still holds.
- **Cards arrive sooner.** They show up minutes after the user goes idle, not whenever the session finally ends, which may be days later.
- **The pattern is already proven here.** `.claude/log-session.py` already rewrites its log after every turn.

## Cons

- **Bandwidth grows quadratically.** Re-uploading the whole `.jsonl` every turn sends far more data than the transcript itself. A long session of 200 turns at several MB each adds up fast. Fix: upload only the bytes added since the last upload (the transcript is append-only), or throttle to at most one upload every 1–2 minutes.
- **Every turn pays a little.** The hook has to detach in about 50 ms or the user feels the delay.
- **Uploads can race.** Two workers for the same session (a fast turn, or two windows) can both upload. That needs a client lock file, or a server check that rejects an out-of-order offset.
- **Extraction has to be incremental.** Re-extracting the whole session would create duplicate cards. Replacing the old cards would wipe review history and schedules. So the server must track how far it has extracted (`processed_through`) and extract only the new turns.
- **Card quality may drop.** The model sees only the new turns, so it can miss context from earlier in the session. Mitigate by also sending it a short summary of the earlier part.
- **The server needs an idle trigger.** Something has to notice "no upload for N minutes" and start extraction, such as a cron sweep. A Vercel cron adds delay, and the sweep has to be safe to run twice.
- **More model calls.** Each idle gap triggers one extraction run, which costs more than one run per session.
- **Privacy.** Partial transcripts leave the machine before the user is done. Someone who wants to discard a session can't, because it has already uploaded. Redaction must run on every upload, and an opt-out or "forget this session" option becomes more important.
- **Shared contract change.** The `sessions` table needs a new migration (for example `uploaded_bytes`, `processed_through`, `last_activity_at`, and a status that can cycle back to pending). Per `AGENTS.md`, the team has to agree before this lands.

## My recommendation

Upload only the bytes added since the last upload, throttled to about once a minute. Run extraction incrementally once a session has been idle for about 10 minutes. Keep `SessionEnd` as a final flush that also triggers extraction straight away.

Not verified: that Claude Code's `.jsonl` stays strictly append-only, including after compaction. Upload-by-offset depends on it.
