## Big picture

CLI login follows the **OAuth 2.0 Device Authorization Grant (RFC 8628)**, the same flow as `gh auth login`. There are two tables:

- **`cli_device_codes`** holds short-lived login attempts. It lasts at most 10 minutes and only the server touches it.
- **`cli_tokens`** holds long-lived bearer tokens that the CLI uses for `push` and `sync`.

## The algorithms

| Thing | How it's made | What's stored |
|---|---|---|
| Device code (the CLI's polling secret) | `randomBytes(32)` as base64url, 43 characters ([device.ts](apps/web/src/lib/tokens/device.ts)) | Only its `sha256` hex |
| User code (what the person types) | 8 letters from `BCDFGHJKLMNPQRSTVWXZ`, picked with `randomInt` (no modulo bias), shown as `XXXX-XXXX` | Stored as is. It is useless without a signed-in approval. |
| CLI token | `sc_` + `randomBytes(32)` as base64url ([hash.ts](apps/web/src/lib/tokens/hash.ts)) | Only its `sha256` hex in `cli_tokens.token_hash` |

**Why plain sha256 and not bcrypt or argon2?** Those are slow hashes, built for low-entropy passwords. These secrets have 256 bits of randomness, so nobody can brute-force them, and a fast hash is enough. If the database leaks, the hashes can't be replayed as tokens. Lookup goes by hash with `.eq("token_hash", …)`, so no stored secret is compared in a timing-sensitive way.

The user-code alphabet has no vowels, so codes can't spell words. It also has no I, O, U or Y, which are easy to misread. There are 20^8 ≈ 25.6 billion possible codes.

## The login flow

1. **`session-coach login`** calls `POST /api/cli/device { clientName }` without a token.
   - The server validates `clientName`: 1 to 100 printable characters, no control characters, so ANSI escapes can't be injected into the approve page.
   - It applies a per-IP rate limit (`deviceStart`, 10 per 10 minutes).
   - It inserts a row with `device_code_hash`, `user_code`, the IP and `expires_at = now + 10 min`. A unique-index clash retries, so two logins never share a code.
   - It returns the raw `deviceCode` once, plus `userCode`, `verificationUri`, `interval: 5` and `expiresIn: 600`.
   - Expired rows older than a day are deleted in `after()`, so no cron is needed.
2. **The CLI opens the browser** to `/cli/approve?code=…`. It uses `open`, `xdg-open` or `rundll32` with no shell, and only for http(s) URLs. The `?code=` in the URL only prefills the form. Nothing is approved without a click.
3. **The person approves** on `/cli/approve`. The page shows the device name and the requesting IP, so they can spot a login they didn't start. Approve and deny ([approve route helper](apps/web/src/app/api/cli/device/route.ts)) run these checks in order:
   1. A same-origin check (CSRF). `Origin` must match exactly. If it is absent, `Sec-Fetch-Site: same-origin` is required. Anything else is refused.
   2. `requireUser()` checks the session against the auth server, not just the cookie.
   3. A per-learner rate limit (`deviceDecide`, 30 per hour), so a signed-in script can't guess other people's codes.
   4. One **compare-and-set** `UPDATE` that matches only rows that are unexpired and undecided. Two tabs, or approve racing deny, can't both win.
4. **The CLI polls** `POST /api/cli/device/token { deviceCode }` ([token route](apps/web/src/app/api/cli/device/token/route.ts)):
   - The row is looked up by `sha256(deviceCode)`. A per-IP limit applies (`devicePoll`, 300 per 10 minutes).
   - `pollOutcome()` returns the RFC 8628 error codes: `authorization_pending`, `slow_down` (the interval grows by 5 s, up to a cap), `access_denied` and `expired_token`.
   - On approval, a second compare-and-set claims `token_issued_at`, so two racing polls can't mint two tokens. Then `createToken()` inserts the `cli_tokens` row and returns the raw `sc_…` token **once**.
   - If minting fails, the claim is released so the next poll can retry.
5. **The CLI saves** `~/.session-coach/config.json` with the directory at mode `0700` and the file at `0600`. It runs `chmod` again even if the file already existed with looser permissions. The URL must be https, except for localhost.
6. **Uploads** send `Authorization: Bearer sc_…`. `requireCliUser()` hashes the token, looks it up, gets the `user_id`, and stamps `last_used_at` after the response.

A token can also be created by hand on `/setup` with `POST /api/cli/tokens`. That route has the same same-origin check, plus `tokenCreate` (10 per hour). Revoking uses `DELETE /api/cli/tokens?id=` through the learner's own RLS client. Another learner's id returns the same 404 as a missing one, so ids can't be probed.

## Database guards

- **`cli_device_codes`**: RLS is on with **no policies**, and `revoke all` from `anon` and `authenticated`. Only the service role can touch it.
- **CHECK constraints make illegal states impossible**:
  - expiry is at most 10 minutes;
  - approved means both `approved_by` and `approved_at` are set;
  - a code is never both approved and denied;
  - a token is issued only for an approved code;
  - the hash is exactly 64 hex characters, and the user code matches the alphabet.
- **`cli_tokens`**: learners can only `select` and `delete` their own rows. There is no insert policy, so minting goes through the service role. Routes select `TOKEN_COLUMNS` and `DEVICE_COLUMNS` by name and never return the hash.

## App-wide measures

- **Headers** ([next.config.ts:15](apps/web/next.config.ts:15)): `frame-ancestors 'none'` plus `X-Frame-Options: DENY` (no clickjacking of the approve button), `nosniff`, HSTS for 2 years, a strict referrer policy, and a Permissions-Policy that blocks camera, microphone and geolocation.
- **Rate limits** use Upstash sliding windows. Unauthenticated actions are limited per IP, using Vercel's unspoofable `x-real-ip`. Costly actions are limited per learner: `push`, `process`, `grade`, `deviceDecide` and `tokenCreate`.
- **No caching or logging of secrets**: every auth response sends `NO_STORE`, and `serverError()` logs only `error.message`, never the body or the token.
- **Redaction** ([redact.ts](packages/shared/src/redact.ts)) scrubs JWTs, `sk-`, GitHub and Google keys, Bearer and Basic headers, `*_KEY=`/`*_TOKEN=` assignments, long opaque strings, emails and home-directory paths from transcripts before upload.
- **RLS everywhere**: learners read only their own rows. Scores, cards and the hidden `model_answer` are written or read by the server with the service role.
- **Server-only code**: `import "server-only"` keeps the admin client and token code out of client bundles.

## Gaps worth knowing

- **CLI tokens never expire and have no scopes.** A leaked `sc_` token works until someone revokes it on `/setup`. The `last_used_at` stamp and the `sc_` prefix (which secret scanners can recognise) only make a leak easier to spot.
- **Rate limits fail open.** Without Upstash configured, or when Redis times out after 1 s, requests are let through. In production this logs an error, and `grade` and `process` are refused instead.

## The CLI token, in plain words

**What it is:** a long random password that belongs to one laptop. The CLI sends it with every upload, so the server knows whose sessions they are.

It looks like `sc_` followed by 43 random characters, for example `sc_Xk3f…`.

### An analogy: a hotel key card

- When you check in (log in), the front desk gives you a **key card** (the token).
- You show the card at the door every time (every `push`), so you don't re-enter your password each time.
- Each device gets its **own card**. Lose one laptop and you cancel only that card on `/setup`. The others keep working.
- The hotel doesn't keep a copy of your card. It keeps only a **fingerprint** of it (the hash). That's the key security idea, explained next.

### How it is made

```
token = "sc_" + 32 random bytes (from the OS's secure random generator)
```

32 random bytes is 256 bits. Guessing it is as hopeless as guessing a specific atom in the universe, so nobody can brute-force it.

The `sc_` prefix does two things:
- a person can tell what it is if they see it;
- secret scanners such as GitHub's can flag it if it is accidentally committed.

### How it is stored: only the fingerprint

The server never saves the token itself. It saves `sha256(token)`, a 64-character fingerprint.

- **sha256 is one-way.** You can turn a token into its fingerprint, but you can't turn a fingerprint back into the token.
- **If the database leaks**, the attacker gets only fingerprints. They can't use them to upload as you, because the server wants the real token.
- **The person sees the raw token exactly once**, when it is created. After that, no one can recover it, not even the server. Lost it? Make a new one.

**Why not bcrypt, like passwords?** Bcrypt is deliberately slow. That protects weak human passwords like `fluffy123` from guessing. Our token is 256 random bits, so guessing is already impossible. A fast hash is safe here and keeps every upload quick.

### How it is used on each upload

1. The CLI reads the token from `~/.session-coach/config.json`. Only your OS user can read that file (mode `0600`).
2. The CLI sends `Authorization: Bearer sc_…`, over HTTPS only. The CLI refuses plain http except to localhost.
3. The server hashes what it received and looks for a row with that fingerprint in `cli_tokens`.
4. If a row is found, the request belongs to that row's `user_id`. If not, the server returns 401: "Unknown CLI token. Run session-coach login again."
5. The server stamps `last_used_at`, so `/setup` shows which tokens are still active.

### How you get one

- **The usual way, `session-coach login`:** the browser opens, you click Approve while signed in, and the CLI receives a fresh token. You never copy and paste anything.
- **By hand on `/setup`:** click create and copy the token once.

Either way, the server creates it. Learners can't insert token rows themselves, because the database allows them only to read and delete their own.

### How you cancel one

Delete it on `/setup`. Its row disappears, so its fingerprint no longer matches anything, and that laptop is logged out at once.

### The one weakness to mention

**Tokens don't expire on their own, and each token can do everything the CLI can do.** A stolen token works until someone revokes it. The defenses are:
- the file permissions;
- the HTTPS-only rule;
- the per-learner rate limits, which cap the damage;
- `last_used_at`, which helps you notice a token you no longer use.

### The one-sentence version

"The CLI token is a 256-bit random key per device. The server stores only its sha256 fingerprint, so a database leak can't be replayed. Each upload proves who you are by presenting the key, and you can revoke any single device on `/setup`."

They are each operating system's built-in command for opening a URL in your default browser. In step 2 the CLI runs one of them so the approve page opens without you copying the link.

| OS | Command | What it does |
|---|---|---|
| macOS | `open <url>` | Opens the URL in your default browser (also works for files and apps) |
| Linux | `xdg-open <url>` | The same, on Linux desktops (GNOME, KDE and others) |
| Windows | `rundll32 url.dll,FileProtocolHandler <url>` | Windows' built-in handler that opens a URL in the default browser |

The code that picks one is `openerFor()` in [device.ts:156](packages/cli/src/device.ts:156).

**"No shell" means the CLI runs the command directly and passes the URL as one argument.** It never builds a command string for `sh` or `cmd.exe` to interpret. That matters because a shell treats characters like `|`, `&`, `^` or `%` as instructions. A URL containing them could make a shell run extra commands. Without a shell, the URL is only ever a URL.

That's also why Windows uses `rundll32` and not the more common `cmd /c start <url>`: `cmd` would reparse the URL and open that hole.

Two more guards:
- The CLI opens only `http` and `https` URLs, so a `file:` or `javascript:` URL can't be launched.
- If opening fails (for example over SSH, or on a machine with no desktop), nothing breaks. The CLI also prints the URL and the code, so you can open it on any device yourself.

Caveman mode is already on, so here is every choice, each with its reason.

## Making the token

- **Why 32 random bytes?** 256 bits cannot be guessed. Short tokens can be brute-forced.
- **Why `randomBytes` from `node:crypto`?** It is the OS's secure random source. `Math.random()` is predictable, so it is never used for secrets.
- **Why base64url?** It is safe in URLs, headers and JSON. It has no `+`, `/` or `=`, so nothing needs escaping.
- **Why the `sc_` prefix?** A leaked token is recognisable. People see what it is, GitHub's secret scanner can flag it, and the CLI rejects a pasted value that lacks it.
- **Why does the server mint it, not the client?** The server controls the randomness and the owner. A learner cannot insert a token row (no insert policy), so nobody can mint a token for someone else.

## Storing the token

- **Why store only `sha256(token)`?** A database leak gives fingerprints, not keys. A fingerprint cannot be turned back into a token, and the server demands the real token.
- **Why sha256 and not bcrypt?** Bcrypt is slow on purpose, to protect weak human passwords. A 256-bit random token has nothing to guess, so slowness buys nothing. A fast hash keeps every upload quick.
- **Why look up by hash, not by comparing strings?** Comparing secrets character by character can leak timing. A hash lookup uses an index, so no stored secret is compared directly.
- **Why show the raw token once?** If the server never stores it, the server can never leak it. Lost token? Make a new one. That is cheap.
- **Why never log the token?** Logs get copied, shipped and read by many people. `serverError()` logs only `error.message`.
- **Why do routes select columns by name?** `TOKEN_COLUMNS` leaves out `token_hash`. Even a fingerprint never leaves the server.

## The login flow (device code, RFC 8628)

- **Why the device flow, not pasting a token?** There is no copy-paste, so the token never sits in the clipboard or shell history. The person logs in through the browser, where their session already exists. It is the same standard `gh` and `az` use.
- **Why two codes?**
  - The device code is the CLI's secret. It never shows on screen.
  - The user code is short, so a person can read and type it.
  - Seeing the user code alone gives nothing, because the token goes only to whoever holds the device code.
- **Why store only the device code's hash?** Same reason as tokens: a leaked row cannot be used to poll.
- **Why the 10-minute expiry?** A short window. An abandoned login dies fast, and a guesser has little time.
- **Why the user-code alphabet `BCDFGHJKLMNPQRSTVWXZ`?** No vowels, so no rude words. No I/O/U/Y, so no confusion with 1/0/V. RFC 8628 suggests this.
- **Why `randomInt`, not `random % 20`?** Modulo makes some letters more likely. `randomInt` is uniform.
- **Why a unique index plus retry on the user code?** Two logins can never share a code. A clash is near impossible, but if one happens it retries and never shares.
- **Why does `?code=` only prefill the form?** Without that, a link from an attacker could approve on click. The person must press Approve themselves.
- **Why does the approve page show the device name and IP?** The person can spot a login they did not start. That is the phishing defense: "I didn't run login on `kali-box` from that IP."
- **Why strip control characters from the client name?** A name containing ANSI escapes or newlines could fake text on the approve page or in a terminal.

## Approve and deny

- **Why the same-origin check?** It blocks CSRF. Without it, another site could make your browser POST approve using your cookie.
- **Why fall back to `Sec-Fetch-Site`?** Some browsers send no `Origin` on same-origin requests. Anything else is refused, never assumed safe.
- **Why `getUser()`, not reading the cookie?** Approving mints a credential, so the session is checked with the auth server. A stale or revoked session fails.
- **Why the compare-and-set update?** It matches only a code that is unexpired and undecided, as one atomic operation. Two tabs, or approve racing deny, cannot both win.
- **Why the 30-per-hour limit per learner?** It stops a signed-in script from guessing other people's user codes.

## Polling

- **Why polling, not a push to the CLI?** The CLI has no public address. Polling works behind any NAT or firewall.
- **Why `slow_down` adds 5 s?** RFC 8628 says so. It punishes a CLI that polls too fast and protects the server.
- **Why 1 s of slack?** Network jitter can land two on-time polls close together. Without the slack, honest clients would get punished.
- **Why are final states checked first?** A denied or spent code answers `access_denied` or `expired_token`, never "slow down". The CLI stops at once.
- **Why the second compare-and-set on `token_issued_at`?** Two racing polls cannot mint two tokens. One code gives one token.
- **Why release the claim if minting fails?** The code is still valid. Without the release, a server hiccup would strand the login as `expired_token`.
- **Why is an approved code past expiry expired?** The CLI should have collected it within the window. A late collector might be an attacker who stole the device code.
- **Why keep expired rows for a day?** `/cli/approve` can then say "expired", which is clearer than "no such code".
- **Why clean up inside `after()`?** No cron is needed, and the login never waits on the cleanup.

## The CLI side

- **Why `0600` on the file and `0700` on the directory?** Only your OS user can read the token. Other users on the machine cannot.
- **Why `chmod` again after writing?** `writeFile`'s `mode` applies only to a new file. An old file with `0644` would stay readable by others.
- **Why HTTPS only, except localhost?** Otherwise the token crosses the network in plaintext. Localhost never leaves the machine.
- **Why `open`, `xdg-open` and `rundll32` with no shell?** A shell would interpret `|`, `&` and `^` inside the URL as commands. Passing the URL as one argument means it is only ever a URL.
- **Why only http(s) URLs?** A `file:` or `javascript:` URL must never launch.
- **Why print the URL as well?** Over SSH or on a machine with no desktop the browser cannot open. You can open the URL on any device instead.

## Each upload

- **Why the `Bearer` header?** It is the standard. Headers do not land in URL logs the way a query string does.
- **Why stamp `last_used_at` after the response?** A failed stamp must not block or slow a valid upload. The stamp shows which tokens are live, so you can spot a dead or stolen one.
- **Why one token per device?** Losing a laptop means revoking one row. Other devices keep working.
- **Why revoke through the learner's RLS client?** The database itself enforces "your own rows only", and the code filters by `user_id` too, so there are two guards.
- **Why does another learner's token id return 404?** It is the same answer as a missing id, so token ids cannot be probed.

## Database

- **Why RLS on `cli_device_codes` with no policies?** Learners never touch the table; only the server does.
- **Why `revoke all` as well?** It is a second guard. RLS mistakes happen, and revoked grants still block.
- **Why CHECK constraints?** The database refuses illegal states even if the code has a bug:
  - approved and denied at once;
  - a token issued for an unapproved code;
  - an expiry longer than 10 minutes;
  - a malformed hash.
- **Why `on delete cascade` on the profile?** When an account is deleted, its tokens die with it, so no orphan keys remain.

## Rate limits

- **Why per IP for start and poll?** There is no user yet, so the IP is the only handle. It stops a flood of logins.
- **Why `x-real-ip`?** Vercel sets it at its edge, so a client cannot fake it.
- **Why per learner for token creation (10 per hour)?** A person makes one or two. A script minting hundreds gets stopped.
- **Why the 1 s Redis timeout and fail open?** If Redis is down, logins still work. The trade is availability over strictness. Supabase's own limits remain behind it.

## App-wide headers

- **Why `frame-ancestors 'none'` and `X-Frame-Options: DENY`?** Clickjacking. Nobody can frame `/cli/approve` and trick you into clicking Approve.
- **Why HSTS?** The browser always uses HTTPS, so there is no downgrade to plain http.
- **Why `NO_STORE` on auth responses?** No proxy or browser cache keeps a token or a code.
- **Why `import "server-only"`?** The admin client and token code can never end up in a client bundle.

## The known gap

**Tokens do not expire and have no scopes.** A stolen token works until it is revoked. The current trade favours convenience: you log in once per laptop. The fix later would be a TTL or scopes.
