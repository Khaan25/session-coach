**Pick: retry a few times (about 3 attempts, with exponential backoff), on network errors and 5xx responses only.**

1. The CLI uploads a session log from a developer's laptop, where Wi-Fi drops, VPNs reconnect and servers hiccup, so most network failures are transient and a short retry turns them into successes without the user doing anything.
2. The upload is a one-shot, user-initiated step (`push --latest`), so a failure leaves the user to rerun the command by hand, and the log has already been redacted, so a retry costs them nothing.
3. Retries should stop at the first 4xx (auth, validation), because retrying those can never succeed and only delays the real error message.

**Trade-off:** you give up the instant feedback of failing fast. When the network is really down, the user waits through the backoff (a few seconds) before seeing the error. Retrying also needs the upload to be idempotent, or a retry after a lost response could create a duplicate session. If the endpoint isn't idempotent yet, add an idempotency key or a content hash before adding retries.
