## 1. `"async": true`

- **What it does:** runs the command in the background so Claude keeps working. "Async hooks can't block or control Claude's behavior: response fields like `decision`, `permissionDecision`, and `continue` have no effect."
- **Supported types:** only `type: "command"`. The field is documented as "only available on `type: "command"` hooks." The reference does not restrict it by event, and it names an async `SessionStart` hook as a valid case.
- **Output to Claude:** after the process exits, Claude Code delivers the JSON response's `additionalContext` and `systemMessage` fields "on the next conversation turn." Neither is shown to you. Plain stdout is not delivered as context; only the JSON fields are documented. The exit code does not reach Claude except via `asyncRewake`.
- **`asyncRewake`:** "runs in the background and wakes Claude on exit code 2. The hook's stderr, or stdout if stderr is empty, is shown to Claude as a system reminder." An idle session is woken immediately.
- **Limits:**
  - Output waits for the next user turn if the session is idle (except `asyncRewake` exit 2).
  - `timeout` is not enforced on an async hook, but it is still enforced on `asyncRewake`.
  - With `claude -p`, running async hooks are killed at teardown and finalized as `cancelled`.
  - Each execution creates a separate background process.
  - An async `SessionStart` hook runs every time the event fires. Its `additionalContext`/`systemMessage` is skipped if identical to what Claude last received, except after compaction or `/clear`.

## 2. `timeout` field

- **Unit:** seconds ("Seconds before canceling").
- **Defaults:** 600 for `command`, `http`, `mcp_tool`; 30 for `prompt`; 60 for `agent`. The `command`, `http`, and `mcp_tool` default drops to 30 on `UserPromptSubmit`, `PreModelSwitch`, and `PostModelSwitch`, and to 10 on `MessageDisplay`.
- **SessionEnd** has its own 1.5 s shared budget, raised to match a larger per-hook `timeout` up to 60 s.
- **Async timeout field:** none. The docs have no `asyncTimeout`. An async command hook is simply not timed out, and `asyncRewake` is still limited by `timeout`.

## 3. SessionStart matchers and stdin

- **Matcher values:** `startup` (new session), `resume` (`--resume`, `--continue`, `/resume`), `clear` (`/clear`), `compact` (auto or manual compaction), and `fork` (a session forked from an existing one, e.g. `--fork-session`). The `fork` row was truncated in the page I could read.
- **Common stdin fields:** `session_id`, `prompt_id`, `transcript_path`, `cwd`, `scratchpad_dir`, `permission_mode`, `effort`, `hook_event_name`.
- **SessionStart-specific stdin fields:**
  - `source`: `"startup"`, `"resume"`, `"clear"`, `"compact"`, or `"fork"`.
  - `model`: may be omitted, for example after `/clear`.
  - `agent_type`: present with `claude --agent <name>`.
  - `session_title`: present when a title is set.
  - When `source` is `"resume"` or `"fork"` and there is a prior response: `seconds_since_last_response`, `context_tokens`, `prompt_cache_likely_expired`, `estimated_cache_write_usd` (Claude Code v2.1.251+).

## 4. Does SessionStart stdout reach Claude?

Yes. The exit-code-0 section says: "The exceptions are `UserPromptSubmit`, `UserPromptExpansion`, `SessionStart`, and `PostModelSwitch`, where Claude Code adds plain-text stdout as context that Claude can see and act on." Structured output also works through `hookSpecificOutput.additionalContext`. SessionStart is limited to `type: "command"` and `type: "mcp_tool"` hooks.

Synchronous SessionStart stdout is added immediately. Async output arrives on the next turn. Your `.claude/session-brief.py` puts standing rules into context, so keep it synchronous (the default) so the rules are present on the first turn.

## settings.json shape

```json
{
  "hooks": {
    "SessionStart": [
      {
        "matcher": "startup",
        "hooks": [
          {
            "type": "command",
            "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/session-brief.py",
            "timeout": 30
          }
        ]
      }
    ]
  }
}
```

Use one matcher group per source you want to handle, or omit `matcher` to run on every SessionStart. The docs' settings example for SessionStart was not in the page sections I could read, so this follows the general matcher-group structure used throughout the reference.
