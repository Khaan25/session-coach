**Short answer:** uploads happen **once, when the session ends**, not after each turn. Duplicates are blocked on the server. But only the server half exists today. `packages/cli` holds just a `package.json`, so no hook or worker has been written yet.

## The planned flow ([docs/ARCHITECTURE.md:7-19](docs/ARCHITECTURE.md:7))

1. Claude Code fires its **`SessionEnd`** hook when you exit, run `/clear`, log out, and so on.
2. The hook reads `session_id` and `transcript_path` from stdin. It starts a **detached worker** and exits within about 50 ms, so Claude Code can't kill the upload partway.
3. The worker redacts and gzips the whole `.jsonl`, then uploads it in 3 steps:
   - **①** `POST /api/sessions` with metadata only. The server inserts a `pending` row and returns a signed Storage URL ([route.ts](apps/web/src/app/api/sessions/route.ts)).
   - **②** `PUT` the gzipped log straight to Storage. It skips Vercel, which caps request bodies at 4.5 MB.
   - **③** `POST /api/sessions/<id>/process` moves the row from `pending` to `processing` and extracts the cards ([process/route.ts](apps/web/src/app/api/sessions/[id]/process/route.ts)).
4. If the upload fails after 3 retries, the worker saves it to `~/.session-coach/outbox/`.

## How duplicates are blocked

- **Database:** `unique (user_id, external_id)` on `sessions` ([init.sql:57](supabase/migrations/20261028000000_init.sql:57)). `external_id` is Claude Code's `session_id`.
- **Step ①, repeat upload:**
  - The row is still `pending` (an earlier try died): you get `409` plus a fresh upload URL, and the log is overwritten (`upsert: true`).
  - The row is already processed: you get `409 { id }`, and nothing happens.
- **Step ③:** a compare-and-set from `pending` to `processing`, so two calls can't both run extraction and create duplicate cards.
- **Client:** the worker skips sessions listed in `~/.session-coach/sent`.

## Your scenarios

- **Close the session normally, or start a new one with `/clear`:** `SessionEnd` fires. That session uploads once. The new session has a new `session_id`, so it becomes a separate row, not a duplicate.
- **Open a second terminal with a new session:** each session gets its own `session_id` and uploads when it ends.
- **Kill the terminal window or crash:** `SessionEnd` may never fire, so that session is never uploaded. The outbox only covers uploads that started and failed. Nothing sweeps for sessions that never ended.
- **Resume a session (`claude --resume` / `--continue`):** this is the real gap. If the resumed session keeps its `session_id`, the worker skips it or the server answers `409 already processed`. The new turns are **silently dropped**. You get no duplicate, but you lose data.

I didn't check whether current Claude Code keeps or changes `session_id` on resume, and that decides how bad the resume gap is. Fixing it touches the shared migration (for example, uploading per transcript segment or a content hash instead of one row per `session_id`), so it needs the team to agree first.
