## Why this matters

Session Coach turns each Claude Code session into 3–5 decision cards and tests the learner on the
"why" on day 1, 3 and 7. Today the web app is one placeholder page: there is no sign-in, no way to
see a session's cards, and no review loop, so nothing a learner can use exists. This plan builds the
public pages (so a visitor understands the product and can install it) and the logged-in dashboard
(so a learner sees sessions arrive, reviews cards and watches progress), on top of a design system
built first so every screen shares one look.

### Phase 4: Sessions list with Realtime status (Zia)

**Scope:** `src/app/(app)/dashboard/page.tsx`, `src/components/sessions/SessionList.tsx`
(client component for the Realtime subscription), `SessionRow.tsx`.

Steps:

1. Server-render the learner's sessions (`id, title, repo, branch, started_at, duration_min,
   status, error, created_at`, newest first, 20 per page; page in the URL with `nuqs`).
2. Subscribe to `postgres_changes` on `sessions` filtered by `user_id=eq.<uid>`; update a row's
   status in place (`pending` → `processing` → `ready` | `failed`) and prepend new sessions.
   Unsubscribe on unmount.
3. Row: title (fallback: repo + branch), relative time, `StatusBadge`, card count when ready,
   failed rows show `error`. Ready rows link to `/s/[id]`.
4. Empty state: "No sessions yet" + link to `/setup`. Error state with retry.
5. "Due today" banner with the count from `reviews` (`due_on <= today` in the learner's
   `profiles.timezone`, not mastered) linking to `/review` (count shows 0 until Phase 6 writes
   reviews).

**Done criteria**: inserting a `sessions` row for the signed-in user from the Supabase SQL editor
appears on the open dashboard within 5 s without a reload, and updating its `status` updates the
badge; a second user's rows never appear (sign in as two accounts or insert a row with
another `user_id`).

### Phase 6: Review queue, quiz and grading (Zia)

**Scope:** `src/app/(app)/review/page.tsx` (queue), `src/app/(app)/review/[cardId]/page.tsx`
(quiz), `src/app/api/review/answer/route.ts`, `src/lib/model/callModel.ts` (if not already
added by Kasam's pipeline work: coordinate, one implementation), `src/lib/review/schedule.ts`
(pure), `src/lib/review/schedule.test.ts`.

Steps:

1. **Schedule (pure, tested first)**: `nextReview(step, score, today)` →
   `{ step, due_on, mastered }`. Score 2: advance step 0→1 (due +1 day), 1→2 (+3), 2→3 (+7),
   step 3 passed → `mastered: true, due_on: null`. Score 0 or 1: step 1, due +1 day. Dates in the
   learner's timezone. **Verify**: `pnpm test` passes the new cases (each transition, a restart,
   mastery, a timezone edge at local midnight).
2. **Grading route** `POST /api/review/answer` `{ cardId, answer }`: validate the body with zod first
   (`cardId` a UUID, `answer` trimmed, 1–4000 characters; 400 on failure) before any query or
   model call, authenticate the learner
   (server client), load the card with the **service role** including `model_answer`, check the
   card belongs to the learner and isn't hidden, call `callModel("grade", …)` with the card's
   why, evidence, model answer and the learner's answer, validate the output with zod
   `{ score: 0|1|2, missing: string }` (retry once on invalid output, then 502), insert `answers`,
   upsert `reviews` with `nextReview`, return `{ score, missing, modelAnswer, nextDue }`. Model
   names only from env vars via `callModel`; never hard-code a provider.
3. **Quiz page**: shows the card's decision and question (not the why), a textarea, submit,
   then the result: score badge, what was missing, the model answer, the evidence, next review
   date. Keyboard: submit with Cmd/Ctrl+Enter.
4. **Queue**: cards due today (`reviews.due_on <= today`, not mastered) plus never-reviewed
   cards from the last 7 days, oldest due first; "Start review" walks them in order.
5. Nav badge with the due count.

**Done criteria**: schedule tests pass; answering a card writes one `answers` row and one
`reviews` row with the expected `step`/`due_on`; the browser never receives `model_answer` before
submitting (check the page's network responses); grading with the model env vars unset returns a
clear 503, not a crash.

**STOP if** the grading model's output doesn't fit `{score, missing}` reliably in 5 manual tries:
report the prompt and outputs; Zia's local grading eval (kept out of the repo) decides the prompt.

## STOP conditions (any phase)

- A step needs a change to `packages/shared` or a new migration: stop, propose it in the team
  channel, and continue only after agreement (shared contract rule).
- A learner-facing query needs `model_answer`, `hidden` cards, or another learner's rows.
- The shadcn lint rules block a design the phase needs: add a variant in `src/components/ui/`
  per the lint message; if that isn't enough, stop and ask instead of disabling a rule.
- Next 16 docs contradict an assumption here (middleware vs proxy, caching, `params` shape).
